# 바이렌워크 — 백업과 되살리기

> 2026-11-05 작성. 무료 Supabase 에는 **자동 백업이 없습니다.** 직접 받아 두지 않으면
> 서버가 날아갔을 때 되살릴 방법이 없습니다.
>
> ⚠️ **이 문서를 다 따라 했다고 해서 '전체 복구가 된다'는 뜻은 아닙니다.**
> 빈 서버에 통째로 부어 본 적이 아직 **없습니다**(7번 참고). 지금 확실한 것은
> "자료를 받아 두었다"까지이고, "되살릴 수 있다"는 **한 번 해 봐야** 압니다.

## 0. 먼저 알아야 할 것 — 자료가 **네 군데**에 나뉘어 있습니다

| 어디 | 무엇 | 관리 화면으로 받나 |
|---|---|---|
| **DB 표 21개** | 직원·인사·결재·근태·일정·메신저 | 13개만 ✅ · 메신저 3개 ❌ · 비밀 설정 ❌ |
| **저장소 3곳** | 결재 첨부, 대화 사진, 직인 | **경로·크기만** ✅ · 본체 ❌ |
| **로그인 계정** | 이메일·비밀번호 (Supabase `auth`) | ❌ 꺼낼 수 없음 |
| **비밀값** | 메일 비밀번호(암호문)·알림 비밀키 | ❌ 일부러 막아 둠 |

**관리 화면의 「업무 자료 내보내기」 하나로는 회사를 되살릴 수 없습니다.**

- 받은 뒤 화면의 **표별 건수**를 눈으로 확인하세요
- 회사 드롭박스 `VIREN_경영/백업/` 에 올립니다

## 2. 매달 — 메신저와 파일 (Supabase 대시보드)

### 2-1. 메신저 3개 표

브라우저로는 못 받습니다. **방에 들어가 있는 사람만 읽을 수 있게** 막혀 있고,
대표님도 예외가 아니기 때문입니다. (이 막음은 일부러 둔 것이고 풀지 않습니다)

**Supabase → SQL Editor** 에서 돌리고 **Download CSV**.
SQL Editor 는 관리자 권한으로 돌기 때문에 **전체가 나옵니다.**

**⚠️ 먼저 건수를 세고 시작하세요.** SQL Editor 는 결과를 한 번에 다 보여주지 않을 수
있습니다. 받은 CSV 의 줄 수가 아래 숫자와 **같아야** 다 받은 것입니다.

```sql
-- ⓪ 몇 건인지 먼저 센다. 이 숫자를 적어 두세요.
select 'rooms' as 표, count(*) from public.rooms
union all select 'room_members', count(*) from public.room_members
union all select 'messages', count(*) from public.messages;
```

```sql
-- ① 대화방
select * from public.rooms order by id;
```

```sql
-- ② 방 참여자
select * from public.room_members order by room_id, user_id;
```

```sql
-- ③ 대화 글 — 건수가 많으면 나눠 받습니다
select * from public.messages order by room_id, created_at, id;
```

**글이 많아 한 번에 안 나오면** 나눠 받으세요. `0` → `5000` → `10000` … 으로
바꿔 가며 받고, 마지막에 **합친 줄 수가 ⓪의 숫자와 같은지** 확인합니다.

```sql
select * from public.messages order by room_id, created_at, id
  limit 5000 offset 0;
```

### 2-2. 파일 본체

**Supabase → Storage** 에서 폴더별로 내려받습니다. **세 곳 모두** 받아야 합니다.

| 저장소 | 무엇 | 지워지나 |
|---|---|---|
| `approval-files` | 결재 첨부 | **안 지웁니다** (근거 문서) |

**받은 뒤 개수와 크기를 맞춰 보세요.** 1번 꾸러미의 `files` 에 저장소별 경로와
바이트 수가 들어 있습니다. 내려받은 폴더의 파일 수·총 용량이 그것과 같아야 합니다.

## 3. 일 년에 한 번 — 구조까지 통째로

표 구조·함수·방아쇠·권한(RLS)은 **우리 코드**에 있습니다 (`supabase/schema.sql`).
깃허브에 있으니 따로 받을 필요는 없습니다. 다만 운영 DB 와 어긋났을 수 있으니
일 년에 한 번은 통째로 떠 두는 편이 안전합니다.

```bash
npx supabase db dump --db-url "<Supabase → Settings → Database → Connection string>" -f viren-work-구조.sql
```

> 비밀번호가 든 주소입니다. **채팅이나 메일에 붙여넣지 마세요.**

### 코드와 운영 DB 가 어긋나지 않았는지

실제로 2026-11-05 에 **`user_mail` 표가 `schema.sql` 에 빠져 있던 것**을 찾았습니다.
운영 DB 에는 있었지만, 코드로 새 서버를 세우면 직원 메일 알림이 통째로 안 섰습니다.
일 년에 한 번은 이렇게 맞춰 보세요.

```sql
-- 운영 DB 의 표 목록. 코드의 schema.sql 과 같아야 합니다.
select table_name from information_schema.tables
 where table_schema = 'public' order by table_name;
```

## 4. 로그인 계정 — **자료보다 먼저**

`employees.id` 는 **로그인 계정 번호(uuid)** 입니다. 계정이 없으면 직원 자료가
안 들어가고, 거기서 모든 게 멈춥니다.

**지금 쓰는 계정 번호를 미리 받아 두세요.** (비밀번호는 안 나옵니다 — 나올 수도 없습니다)

```sql
-- 계정 번호와 메일 주소만. 매달 1번과 같이 받아 두세요.
select u.id, u.email, u.created_at
  from auth.users u order by u.created_at;
```

되살릴 때는 **같은 uuid 로** 계정을 다시 만들어야 합니다.
Authentication 화면에서는 uuid 를 정할 수 없으므로 **SQL 로 넣어야 합니다** —
이 부분은 **혼자 하지 말고 담당에게 요청하세요.**

> 비밀번호는 아무도 되살릴 수 없습니다. 새 비밀번호를 정하고 직원들에게
> 바꾸게 하는 수밖에 없습니다.

## 5. 되살리는 차례

### ① 구조
`supabase/schema.sql` 을 SQL Editor 에 붙여넣고 Run.

### ② 알림을 먼저 꺼 둡니다 — **안 그러면 알림이 터집니다**
```sql
update public.push_config set url = null where id = 1;
```

### ③ 로그인 계정 (4번)

### ④ 업무 자료
**관리 → 기타 설정 → 되돌리기 → 「꾸러미 열기」**

1. 꾸러미가 성한지 **검사**합니다 (판 번호·받은 때·건수·해시·줄 모양)
2. 무엇이 몇 건 들어가는지 **미리 봅니다**
3. **검사를 통과해야만** 「되돌리기 SQL 만들기」가 눌립니다
4. 내려받은 `.sql` 을 **열어서 읽어 본 뒤** SQL Editor 에 붙여넣기

> 이 SQL 은 **한 덩어리로** 돕니다. 중간에 하나라도 걸리면 아무것도 안 들어간 채
> 되돌아갑니다. 다만 **같은 번호의 줄은 덮어씁니다.**

### ⑤ 메신저
2-1 의 CSV 를 **rooms → room_members → messages 차례로** 넣습니다.

### ⑥ 파일
2-2 의 파일을 **같은 경로로** 올립니다. 경로가 다르면 첨부가 안 열립니다.

### ⑦ 비밀값 다시 넣기 (6번)

### ⑧ 알림 다시 켜기
```sql
update public.push_config set url = 'https://work.viren.kr/api/notify' where id = 1;
```

## 6. 비밀값은 백업하지 않습니다 — 다시 넣습니다

**일부러 뺀 것입니다.** 비밀번호나 열쇠가 일반 JSON 파일에 섞여 드롭박스를 돌아다니면,
파일 하나가 새는 순간 회사 메일함까지 열립니다.

| 무엇 | 어디에 | 어떻게 되살리나 |
|---|---|---|
| `push_config.secret` | DB (브라우저에서 못 읽음) | 새 값을 만들어 **Cloudflare 환경변수와 DB 양쪽**에 같게 넣습니다 |
| `push_config.url` 등 | DB | 새 서버 주소로 다시 넣습니다 |
| **VAPID 열쇠** | Cloudflare 환경변수 | 새로 만들면 **직원들이 알림을 다시 켜야 합니다** |
| `user_mail.secret` | DB (암호문) | **되살릴 수 없습니다.** 직원이 각자 메일 비밀번호를 다시 넣습니다 |
| `MAIL_KEY` | Cloudflare 환경변수 | 이게 없으면 암호문을 못 풉니다. 따로 안전하게 보관하세요 |

> `user_mail.secret` 은 암호문이고 푸는 열쇠는 Cloudflare 에만 있습니다.
> **둘 다 있어야** 열립니다. 백업에 넣지 않는 이유이자, 넣어도 쓸모가 없는 이유입니다.

## 7. 되살릴 때 터지는 부작용 — 미리 막으세요

### ⚠️ 메일이 한꺼번에 다시 옵니다
`mail_state` · `user_mail.last_uid` 는 **"어디까지 봤는지"** 입니다.
과거 값으로 되돌리면 그 뒤에 온 메일을 **전부 새 메일로 보고** 알림을 쏟아냅니다.
→ **백업에 넣지 않습니다.**

### ⚠️ 알림이 엉뚱한 기기로 갑니다
`push_subs` 는 기기 등록입니다. 옛 등록을 되살리면 이미 지운 앱으로 계속 쏩니다.
→ **백업에 넣지 않습니다.** 직원들이 '내 정보 → 기기 알림'에서 다시 켭니다.

### ⚠️ 되살리는 동안 알림이 터집니다
자료를 넣으면 방아쇠가 돌아 알림이 나갑니다.
→ 5번 ②·⑧ 처럼 **앞뒤로 꺼 두세요.**

## 8. 다 됐는지 확인하는 법

되살린 뒤 아래를 **전부** 확인해야 "됐다"고 할 수 있습니다.

- [ ] 표별 건수가 꾸러미의 `counts` 와 같다
- [ ] 메신저 3개 표 건수가 2-1 ⓪ 의 숫자와 같다
- [ ] 저장소 3곳의 파일 수·총 용량이 꾸러미의 `files` 와 같다
- [ ] 직원이 **로그인된다**
- [ ] 결재 문서를 열면 **첨부가 열린다** (경로가 맞다는 뜻)
- [ ] 증명서가 뽑힌다 (인사·경력·자격 기록이 들어갔다는 뜻)
- [ ] 메신저 방이 보이고 지난 글이 있다
- [ ] 시험 알림이 **뜬다**
- [ ] 메일 알림이 **지난 메일을 다시 쏟지 않는다**

## 9. 지금 안 되는 것 (솔직하게)

- **자동 백업이 없습니다.** 사람이 매달 눌러야 합니다.
- **되살리기를 실제로 해 본 적이 없습니다.** 코드와 SQL 은 시험했지만,
  빈 서버에 통째로 부어 본 적은 없습니다. **이것이 가장 큰 미검증 항목입니다.**
- **메신저·파일·계정은 손으로 받아야 합니다.** 자동화되어 있지 않습니다.
- **로그인 비밀번호는 되살릴 수 없습니다.** 새로 정해야 합니다.
- **파일이 많아지면** 저장소에서 내려받는 데 오래 걸립니다.
